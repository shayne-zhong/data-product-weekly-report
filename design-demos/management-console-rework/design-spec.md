# 管理后台重设计 · 共用设计说明

## 项目与交付

本次只制作供评审的三份独立 HTML 高保真原型，不接入真实接口、不修改 `public/index.html`、不提交任何实际配置。产品是“部门工作台”的管理后台，面对全局管理员与部门负责人；使用场景是工作日桌面端处理组织设置、成员权限、归档策略、AI 密钥及定时任务异常。输出均为单文件 HTML，默认桌面画幅 1440 × 960，同时在窄屏下保持可读。每份文件开头必须写明：这是原型、使用的假设、示例数据不代表生产状态、尚未解决的事项。所有内容使用中文，避免空泛宣传式文案。

## 已知业务与信息边界

后台默认进入“管理概览”，内容按待处理事项优先排序：定时任务失败、缺少部门负责人、模块负责人未配置模块、历史任务负责人无法唯一匹配、应归档而未归档的总结。二级页面固定在顶部两级导航内：组织管理（部门管理、成员管理）、规则配置（保持登录、归档设置）、系统运维（API 密钥、定时任务）。当前 PRD 明确后台内容区不增加左侧导航，因此三份方案都必须保留顶栏两级导航，不可将产品改成左侧栏管理系统。全局管理员可访问全部导航；部门负责人只见组织管理且只能维护本部门允许的内容。真实服务端权限、保存逻辑和高风险确认规则在原型中不可弱化。

## 核心流程与状态

每份原型至少可演示：进入管理概览；点击或聚焦一级导航打开二级菜单；进入部门管理或成员管理；展示“全局管理员 / 部门负责人”角色可见性差异；对一处普通配置做出未保存修改并显示页面级保存栏与菜单脏标记；点击“检查并补跑”打开明确说明不可重复创建或提前归档的确认弹窗。部门和成员页面应是高密度数据列表，不再把整行字段同时变成编辑控件；单条详情可采用抽屉或受控详情面板。保持登录、归档设置和 API 密钥是分组表单。定时任务页必须区分从未执行、执行中、成功、失败，呈现执行时间、来源、范围、业务结果与经过脱敏的失败摘要。API 密钥仅显示掩码状态，不得展示或模拟真实密钥。

## 设计要求

界面气质应当是稳健、可审计、任务导向而非营销化。信息密度应服务于异常定位和安全操作；避免无业务含义的 KPI、装饰图标、用户评价、填充数据和全屏渐变。示意记录必须清楚标为“示例数据”，不伪装为真实统计。禁止 emoji、SVG 人物或场景插画、无依据的性能数字、紫蓝霓虹和千篇一律 bento 卡片。使用 CSS Grid、清晰分隔线、正常对比度、可访问焦点和最小 44px 的关键点击目标。页面至少包含一个应被用户记住的视觉签名，但该签名应来自信息组织、排印或控制台交互，而不是装饰特效。

## 品牌与素材

现有产品只有代码内的红色工作台标识，无可用官方图片、外部品牌素材或已授权照片。图像不是本任务的内容必需物，因此不使用图库、人物图、产品渲染或伪造插画。沿用现有红色标识的几何 SVG 仅作品牌锚点；不创造新 Logo。页面可以基于现有红、白、灰的视觉遗产做色阶扩展，但不要求复刻上一轮 dp-design 原型。所有按钮、状态与文本需用真实业务语义；不要把“成功”或“失败”仅用颜色表达。

## 三份方向

1. `01-angled-command.html`：秒数轮盘结果为网页风格库第 14 项“Angled Fluid Gradient”。将其转化为克制的红色斜切信息层，不使用全屏多色渐变；重点探索“行动优先”的概览与异常事项编排。
2. `02-institutional-operations.html`：现实参照检索两次均因连接失败，禁止虚构外部案例或声称借鉴某品牌。以项目现有 PRD、管理任务与审计边界为唯一事实来源，探索制度化运营台：强网格、可追溯状态、低装饰、高可读。
3. `03-editorial-control-room.html`：采用“顶级信息设计师为复杂运营流程做版式”的定制逻辑，探索编辑化排印、强层级和克制但可记忆的摘要区；不可牺牲任务密度，也不可把管理后台做成杂志封面。

## 验收

每个文件应可双击打开并无外部依赖；控制台没有 JavaScript 错误；所有演示按钮能完成其对应前端状态切换；角色切换不显示无权导航；Esc 能关闭菜单、抽屉或弹窗。三份文件必须保持相同的信息架构和演示范围，差异只来自视觉、排版和空间组织，便于横向选择。原型完成后执行独立 HTML 语法与交互选择器检查；若浏览器或 Playwright 无法访问工作区文件，明确记录限制，不绕过安全策略。
