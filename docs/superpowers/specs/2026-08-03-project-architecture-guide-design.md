# 项目架构公共文档设计

## 目标

为本项目建立一份稳定、低成本的架构入口，使 Codex 在每个任务开始时先获得必要的项目上下文，再根据任务定向读取代码，不再因用户未指定文件而先询问入口。

## 采用方案

在仓库根目录新增 `PROJECT_ARCHITECTURE.md`，作为项目架构的唯一公共入口；在 `AGENTS.md` 中把它设为每个任务的必读文档。

保留小范围读取、限制无目的扫描和优先读取相关符号等预算规则。仅删除“用户未指定文件时不得探索、必须先询问入口”的限制，改为允许 Codex 根据架构文档进行有目的的定向探索。

## `PROJECT_ARCHITECTURE.md` 内容

文档只记录稳定且可验证的信息：

1. 项目用途、运行方式和主要技术栈；
2. 前端入口、后端入口及部署适配层；
3. 核心目录与模块职责；
4. 主要请求、数据与持久化流程；
5. 测试目录及其对应模块；
6. 常用开发、构建和验证命令；
7. 架构文档的更新条件。

文档不复制实现代码、不记录临时任务状态，也不替代 `PRD.MD`、`PROJECT_STATUS.md` 或 `SESSION_HANDOFF.md`。

## 任务启动规则

每个新任务先读取 `PROJECT_ARCHITECTURE.md`。随后根据任务关键词选择最少的入口文件、模块或测试进行定向读取。只有架构文档缺失、明显过期或任务涉及未覆盖区域时，才扩大探索范围。

## 整理方法

首次生成架构文档时，以运行脚本和真实入口为起点，依次核对前端、服务端、API、共享库、部署函数和测试映射。忽略依赖目录、构建产物、备份和大型日志。所有架构结论必须能对应到实际文件或配置。

## 更新规则

当入口、目录职责、数据流、部署方式或测试映射发生变化时，相关开发任务必须同步更新 `PROJECT_ARCHITECTURE.md`。仅修改页面文案、样式或局部业务逻辑时无需更新。

## 风险与控制

- 文档过期：通过架构变更同步更新规则控制。
- 启动上下文增加：保持单文件、摘要化，不复制代码。
- 探索范围失控：继续保留读取预算和禁止无目的扫描规则。
- 误纳用户改动：除本次明确需要修改的 `AGENTS.md` 外，设计文档、规则和架构文档分别核对差异并单独提交。

## 验收标准

1. 根目录存在结构清晰的 `PROJECT_ARCHITECTURE.md`；
2. `AGENTS.md` 明确要求任务开始先读架构文档；
3. `AGENTS.md` 不再要求用户未指定文件时先询问入口；
4. 架构文档中的入口、脚本和模块映射均由当前仓库文件验证；
5. 除本次明确纳入的 `AGENTS.md` 外，用户现有未提交改动不被覆盖或纳入本功能提交。
