# 后台管理中心与数据看板设计

## 1. 背景与目标

当前后台按功能逐项堆放，账号与部门成员、全局与部门工作模块存在重复入口，登录、归档、AI 和定时任务等不同风险等级的操作混在同一配置流中。此次调整将后台从“配置页集合”重组为角色化管理中心，并新增以待处理事项为核心的数据看板。

目标：

1. 让管理员按管理职责找到功能，而不是记忆功能名称。
2. 让全局管理员和部门负责人只看到其职责范围内的数据与操作。
3. 将组织维护、业务配置、安全配置和运行操作明确分层。
4. 通过看板发现异常并下钻处理，所有数字具备明确口径。
5. 对高风险操作提供独立确认、审计和防重复保护。

非目标：

- 不建设经营分析大屏、自定义图表或趋势预测。
- 不增加数据导出、批量角色调整和批量删除。
- 不改变现有业务数据结构中的 `modules` 等兼容字段。
- 不重构与后台管理无关的工作台页面。

## 2. 方案选择

采用“按职责重组 + 角色化数据范围 + 行动型看板”。相比只调整菜单，它能同时解决入口、权限和操作风险问题；相比为不同角色建设两套后台，它可复用同一页面和权限策略，避免重复维护。

## 3. 信息架构

```text
后台管理
├─ 管理概览
├─ 组织与权限
│  ├─ 部门管理
│  ├─ 成员管理
│  └─ 角色与负责范围
├─ 业务配置
│  ├─ 工作模块
│  ├─ 总结归档规则
│  └─ AI 服务
├─ 系统与安全
│  ├─ 登录策略
│  └─ 操作审计
└─ 运行中心
   ├─ 定时任务
   └─ 执行记录与异常
```

界面统一使用“工作模块”，代码和持久化继续兼容现有 `modules` 命名。成员管理合并现有账号管理与部门成员入口；工作模块管理合并全局与部门入口，通过角色决定数据范围和按钮权限。

## 4. 角色与可见范围

| 能力 | 全局管理员 | 部门负责人 | 普通用户 / 模块负责人 |
| --- | --- | --- | --- |
| 管理概览 | 全部或指定部门 | 仅本部门 | 不可访问后台 |
| 部门管理 | 新增、编辑、停用 | 只读本部门 | 不可访问 |
| 成员管理 | 全部部门 | 本部门普通用户与模块负责人 | 不可访问 |
| 部门负责人 | 指定或更换 | 不可修改 | 不可访问 |
| 工作模块 | 全部部门 | 仅本部门 | 不可访问 |
| 归档规则、AI、登录策略 | 可维护 | 不可访问 | 不可访问 |
| 定时任务、执行记录、补跑 | 可查看和操作 | 不可访问 | 不可访问 |
| 操作审计 | 全部记录 | 仅本部门非敏感记录 | 不可访问 |

服务端必须在读取、统计和修改前应用同一角色范围。越权访问返回无权限，不通过空数据暗示对象是否存在。

角色保护规则：

- 每个部门最多一名部门负责人。
- 更换负责人时必须同时选择原负责人的新角色，服务端原子提交。
- 部门负责人不能修改负责人角色或跨部门成员。
- 模块负责人必须至少关联一个工作模块。
- 仍被指定为部门负责人的成员账号不能直接停用，必须先完成负责人更换；全局管理员凭证沿用独立的服务端管理身份，不纳入普通成员账号启停。

## 5. 管理概览

### 5.1 页面结构

页面从上到下依次为：范围与周期、待处理事项、运行异常、任务与总结概况、组织概况、AI 服务状态。异常数量显示在相关导航项上。

全局管理员可切换“全部部门”或一个部门；部门负责人固定为本部门。周期支持本周、本月、本季度。页面展示最后统计时间和手动刷新按钮。

### 5.2 指标口径

| 指标 | 口径 |
| --- | --- |
| 启用部门数 | 当前范围内状态为启用的部门数量 |
| 启用 / 停用成员数 | 当前范围内按账号启用状态计数 |
| 角色人数 | 当前范围内启用账号按有效角色计数 |
| 周期任务数 | 归属于所选周期和授权范围的任务数量 |
| 已完成任务数 | 周期任务中状态为“已完成”的数量 |
| 任务完成率 | 已完成任务数除以周期任务数；分母为零时显示“—” |
| 历史未完成任务 | 归属周期早于当前周期且状态不是“已完成”的任务 |
| 总结完成情况 | 所选周期内已保存、已归档和缺失的总结数量 |
| 应归档未归档 | 已到配置归档时间但仍未归档的总结数量 |
| 运行状态 | 每类定时任务最近一次执行状态、时间和业务结果 |
| AI 服务状态 | 启用状态、密钥是否已配置、最近测试结果；不返回密钥 |

首版不计算同比、环比和预测值。任务和总结指标只使用现有持久化数据，不为看板制造新的业务状态。

### 5.3 待处理事项

待处理项按“运行失败、权限或组织异常、业务数据异常、提醒”排序，同级按发生时间倒序。至少包含：

- 定时任务失败；
- 应归档但未归档的总结；
- 启用部门缺少部门负责人；
- 模块负责人未关联工作模块；
- 历史任务负责人无法唯一匹配账号。

每项展示类型、影响范围、发生或发现时间、处理入口。点击后跳转到对应页面并保留 `departmentId`、`periodType`、`periodKey` 和状态筛选；用户无权访问的下钻目标不得返回数据。

## 6. 页面交互

### 6.1 导航与范围

- 后台入口默认进入管理概览。
- 页面标题显示“页面名称｜当前部门范围”。
- 返回工作台时恢复进入后台前的业务页面和筛选状态。
- 导航异常徽标只显示当前授权范围内的数量。

### 6.2 保存与离开

- 每个页面独立保存，不保留跨页面全局保存条。
- 首次修改后显示“有未保存内容”；切换页面或离开后台前确认。
- 保存期间禁用重复提交；失败时保留输入并显示可重试原因。
- 保存成功说明具体对象和结果，例如“已更新数据产品部 3 名成员”。

密码重置、账号停用、负责人更换、AI 密钥清除和检查并补跑使用独立请求与确认框，不进入普通配置保存。

### 6.3 列表

成员、部门和工作模块列表支持适用的关键词、部门、角色和启用状态筛选。数据量超过单页上限时分页；首版默认每页 20 条。列表显示最近修改时间，默认提供停用而非删除，不提供批量删除。

成员页面使用“列表查看 + 详情编辑”，避免在单行同时出现多个输入框。筛选无匹配时保留筛选条件并提供清除入口。

### 6.4 状态反馈

所有页面区分：加载中、空数据、无匹配结果、无权限、加载失败。加载失败保留页面结构并允许重试；无权限不展示对象详情。连续操作期间按钮禁用并显示进行状态。

## 7. 运行中心

定时任务列表分别展示计划状态和执行状态。执行状态为从未执行、执行中、成功、失败；执行来源为自动调度、启动补偿、管理员手动运行。

执行记录展示任务名称、来源、开始与完成时间、源周期、目标周期、检查范围、成功数量、跳过数量、失败数量和截断后的错误摘要。

人工操作统一命名为“检查并补跑”，确认内容为：“只处理已经到期但尚未完成的内容，不会重复创建或提前归档。”单次点击仅产生一次请求，复用现有防重和到期判断，不增加自动重试。

## 8. 操作审计

审计范围包括角色变更、账号启停、密码重置、部门负责人更换、AI 密钥配置或清除、登录策略修改、归档规则修改和人工补跑。

记录字段：`id`、`actorUsername`、`actorRole`、`departmentId`、`action`、`targetType`、`targetId`、`result`、`summary`、`createdAt`。摘要只保存必要的前后变化，不保存密码、完整密钥、会话令牌、请求头或堆栈。

记录保留最近 180 天且最多 5,000 条，清理时删除最旧记录。写审计失败不能把已经成功的业务操作回滚，但必须产生受控错误日志并在运行健康状态中提示审计写入异常。

## 9. 技术边界与数据流

建议新增独立领域模块 `lib/admin-dashboard.mjs`，负责指标口径、异常识别和授权范围内的聚合；API 处理器只负责鉴权、参数校验和响应。审计逻辑放在独立服务中，由高风险管理操作显式调用。

```text
后台页面
  → 管理 API 鉴权
  → 解析角色与部门范围
  → 看板聚合 / 管理领域服务
  → state-store 读取或写入
  → 返回已裁剪数据
  → 页面渲染、下钻或提示
```

看板查询参数限定为允许的部门、周期类型和周期键；服务端忽略或拒绝超出角色范围的部门参数。聚合响应返回 `generatedAt`、`scope`、`period`、`metrics`、`alerts` 和 `health`，不返回原始敏感配置。

首版优先直接聚合现有状态数据。只有验证显示响应时间不可接受时才增加短期缓存；缓存键必须包含角色范围、部门和周期，任何相关管理写入后失效。

## 10. 错误与边界

- 无有效分母的比例返回 `null`，界面显示“—”。
- 数据项缺少部门或周期时不猜测归属，进入数据异常或从相关指标排除，并说明排除数量。
- 单个异常项解析失败不得阻断整个看板；返回受控的部分结果和健康提示。
- AI 状态只表示启用、密钥已配置和最近测试结果，不代表供应商实时可用。
- 执行中任务刷新页面后仍以服务端持久化状态为准。
- 所有错误摘要截断并清除密钥、请求头和堆栈等敏感内容。

## 11. 修改范围

- `PRD.MD`：增加后台管理中心、看板、角色保护和审计要求。
- `public/index.html`：重组导航、页面、看板、列表、独立保存和状态反馈。
- `api/[...path].mjs`：增加授权后的看板聚合与审计查询入口，统一后台权限调用。
- `lib/admin-dashboard.mjs`：集中实现指标和异常口径。
- 独立审计服务及对应持久化结构。
- 对应领域、API、权限和 UI 行为测试。

具体文件拆分在实施计划阶段根据现有 API 与状态结构定向确认，不在设计阶段扩大重构范围。

## 12. 验收标准

1. 全局管理员进入后台默认看到全部部门管理概览，可切换部门和周期。
2. 部门负责人只看到本部门概览、成员和工作模块，不显示全局配置与运行入口。
3. 普通用户和模块负责人无法访问后台页面数据及相关接口。
4. 看板指标与相同筛选条件下的任务、总结、成员和执行记录逐项一致。
5. 分母为零的完成率显示“—”，每个指标可查看口径。
6. 待处理事项可下钻并保留部门、周期和状态筛选。
7. 账号与部门成员、两套工作模块入口分别合并，历史数据无需迁移即可正常显示。
8. 每个页面独立保存；离开未保存页面会提示，保存失败不丢失输入。
9. 仍被指定为部门负责人的成员不能直接停用，负责人更换和模块负责人范围满足保护规则。
10. “检查并补跑”只处理到期且未完成内容，重复运行不会重复创建或提前归档。
11. 高风险操作生成不含敏感信息的审计记录，越权用户无法读取记录。
12. 相关权限、统计口径、异常边界、API 和 UI 行为测试通过。

## 13. 实施顺序建议

1. 统一后台权限策略和角色保护。
2. 合并成员与工作模块入口，完成信息架构迁移。
3. 建立看板聚合模块、指标口径和下钻参数。
4. 拆分独立保存与高风险操作。
5. 增加操作审计和运行记录展示。
6. 完成针对性测试与角色验收。
