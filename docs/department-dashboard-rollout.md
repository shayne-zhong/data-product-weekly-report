# 部门驾驶舱取数与实施指南

本次交付是本地后台首页、授权读取、JSON/CSV 预检及确认导入；不包含推送、部署、外部连接器、定时抓取或外部凭证配置。正式发布需要另行授权。字段和接口以 [v1 供数文档](department-dashboard-api.md) 为准。

## 1. 当前可用程度

| 数据块 | 当前路径 | 使用限制 / 下一步 |
| --- | --- | --- |
| 启用网站账号、已保存任务及完成记录 | 工作台直接聚合 | 明确为账号和任务记录，不能改称 HR 人数或重点任务 |
| 部门目标与任务贡献 | 工作台直接聚合 | 保留原目标与贡献规则；个人考核比例和外部实测值不能自动推导 |
| 外部指标文件导入 | 后台已实现 | 人工导入，按批次记录业务截止、接收时间和覆盖；刷新页面不抓取来源 |
| 外部提供方查询接口 | 本文档给出待建设协议 | 先核实能力、权限和数据定义，再安排建设 |
| 自动同步、服务身份、凭证轮换 | 尚未建设 | 本次不配置，不承诺自动刷新 |
| 外部历史趋势 | 仅展示已导入有效历史 | 采集前留空，不用当前值补历史 |

每次查看来源状态，分别判断“能力是否具备”和“本次是否拿到有效数据”。API 已写好不代表生产来源已接入；本地验证通过不代表生产已上线。

## 2. 谁负责什么

以下是责任角色，实际姓名由部门指定，不假定已有负责人。

| 角色 | 必须交付 | 确认点 |
| --- | --- | --- |
| 部门业务负责人 | 指标定义、所选部门、年度目标、覆盖限制、权威来源 | 数字是否能用于管理决策 |
| 工作台管理员 | 真实部门 ID / 账号映射、导入操作、预检核对、批次留档 | 权限和范围正确，未导入演示数据 |
| 数据源管理员 | 原生接口能力或正式导出、数据字典、业务截止和历史范围 | 统计口径与源系统查询一致 |
| BI / 数据治理责任角色 | 访问、目录、覆盖率、质量的分子分母和去重口径 | 流量/存量/比例分开，范围可追溯 |
| AI 平台责任角色 | 成功调用、Token 账本、应用清单、部门归属 | 渠道是否覆盖、账单是否重叠 |
| HR / 人才评估责任角色 | 在职人数、人员归属、能力评估台账 | 网站账号与在职、能力层级不混用 |
| 发布与验收责任角色 | 经授权的发布操作和上线核验记录 | 本地与生产独立验收 |

## 3. 按优先级接入，不等待一次收齐

| 阶段 | 可执行动作 | 退出条件 |
| --- | --- | --- |
| 0：网站真实数据 | 在选定部门查看账号、任务、贡献；与现有后台同范围核对 | 部门、期间和定义明确；外部缺数保持灰色 |
| 1：BI 小试点 | 选 1 部门、1 来源、1 期间，导入访问次数/报表目录/活跃率中的已确认项 | 与源系统同一查询核对；分子分母一致；刷新后仍可追溯 |
| 2：Token | 核实账单或日志中部门归属；先接 1 个能可靠归属的渠道 | 清楚标注已接入渠道；输入、输出、缓存不重复计；无权限渠道仍缺数 |
| 3：HR | 由 HR 提供同截止日在职人数；人才评估另行确认 | 人数与名册一致，账号数独立显示；未评估者不推定等级 |
| 4：扩展资产与质量 | 指标目录、仓库分层、API 清单、六性测量、应用与人才台账逐项接入 | 每项有正式定义、来源、责任角色、频率和核验样本 |
| 5：自动化另案 | 评估提供方 API、来源服务身份、预算和重试限额 | 单独批准方案及发布；生成与校验分开，不让拉取结果自行宣告合格 |

BI → Token → HR 为默认试点顺序，可按部门业务价值调整。没有真实数据的项目继续灰显；不要为了版面完整先填估计值。

## 4. 发给数据提供方的请求

以下文本可直接复制，先补齐方括号内容再发送：

> 我们正在建设[部门名称]的管理驾驶舱，拟由贵方作为[指标名称]的正式数据来源。请先确认能否按部门和统计期间提供数据，不要求本轮立即开发接口。
>
> 请提供：①来源系统与责任角色；②部门映射及稳定 ID；③指标定义、去重/有效状态规则、单位；④期间首尾日及业务截止时间；⑤比例的同口径分子与分母；⑥覆盖哪些对象/渠道及缺口；⑦历史最早可追溯日期、更新频率和失败处理；⑧可授权 API 或正式 CSV/JSON 导出方式。
>
> 若可开发查询接口，请按随附《部门驾驶舱供数接口与文件格式 v1》的“外部提供方查询协议”评估。该协议尚未自动接入工作台，来源服务身份须另行约定；请勿索取或使用工作台完整管理员令牌。若暂不具备 API，请先按同一 v1 模板导出，管理员可人工预检后导入。
>
> 首轮只试点[部门 ID]、[sourceId]、[periodStart]至[periodEnd]。请附同范围原生系统查询/汇总结果供核对；未知项目留缺口，不填 0，不用示例数代替。业务定义与数据由双方责任角色确认后再用于正式看板。

## 5. 各来源最小供数清单

| 来源 / 数据提供方 | metric / 最小材料 | 口径必须确认 |
| --- | --- | --- |
| BI 访问统计 | `report_visits`；有效访问汇总、查询范围 | 排除健康检查与重试；部门归属与访问事件去重 |
| 数据 AI 网关 | `data_ai_calls`；业务请求统计 | 成功请求口径、请求 ID 去重；与周报提炼调用分开 |
| BI 目录与访问日志 | `report_count`, `report_active_rate`, `business_users` | 唯一报表、已发布未下线状态；活跃分子分母同范围；用户是有效、累计还是活跃 |
| 治理规划/指标目录 | `data_coverage`, `metric_count` | 同版规划分母与已验收分子；有效指标唯一 ID |
| 仓库元数据 | `warehouse_table_count`，可带 `warehouse_layer` | 有效表清单、分层名称、期末存量；容量不冒充表数量 |
| API 目录 | `service_api_count` | 已发布可用唯一接口；接口数与调用数分开 |
| 质量平台 | `quality_pass_rate`，`领域|六性` | 规则版本、参检量/通过量、执行截止；未检测维度留空 |
| 模型网关/供应商账单 | `token_total`, `token_input`, `token_output` | 部门、期间、渠道/领域归属；缓存/推理是否已含，避免重叠累加 |
| AI 应用台账 | `ai_app_count`, `ai_active_app_count` | 唯一应用、上线状态、主要领域和承载方式；账号/对话/提示词不当应用 |
| 人才评估台账 | `ai_talent_count` | 经确认评估、部门归属、主要层级互斥；当前看板只代表所选部门 |
| HR 名册 | `hr_employees` | 在职标准、截止日、组织归属；账号停用不自动等于离职 |
| 个人绩效正式结果 | `employee_goal_rate`, `employee_key_task_rate` | 本部门网站 username、考核期间、目标/重点定义及分子分母；不能按全部任务推定 |

## 6. 人工导入操作

1. 登录后台并明确选择部门、年份与期间；从来源面板确认当前缺数和已有来源，点击“导入数据”。
2. 从导入窗口下载空模板：[JSON 文件](../public/dashboard-templates/blank.json)、[CSV 文件](../public/dashboard-templates/blank.csv)；网站直接地址分别为 `/dashboard-templates/blank.json`、`/dashboard-templates/blank.csv`。复制真实部门 ID、稳定来源 ID，生成本部门唯一批次 ID，填业务源 `asOf`。CSV 各行文档级字段必须相同，完整 18 列均需保留，列顺序可调整。
3. 将源系统正式结果转换为 v1。使用网站当前展示的期间边界；累计量提供完整期间，存量提供期末快照，比例提供分子分母。仅有片段时不要伪装成完整期间。
4. 选择 CSV/JSON 文件并点击“校验与预览”。核对授权部门、来源、业务截止、期间、记录数、覆盖、维度及是否覆盖已有键。每批最多 500 条，原始 JSON 请求连同外层字段和空白总计不得超过 1 MiB；近上限文件应拆成不同批次。任何错误先回到源文件修正，不绕过预检。
5. 由责任角色核对至少一项累计量、一项存量和一项比例（仅对本批实际含有的类型），确认后点击“确认导入”。网站会再次校验，预检本身不入库。
6. 刷新后查看来源、人工导入标识和更新时间；抽查显示值及分母，再保存源文件、批次 ID、来源查询凭据和核对结果。不要把管理员令牌写入留档材料。
7. 需更正时导出新真实结果，使用新批次 ID 和不早于原结果的 `asOf`；重新预检。相同批次仅用于相同内容重试。

接口暂不可用时，让上游按相同口径导出 CSV/JSON；导入、校验、权限、覆盖和来源规则完全相同。若其原生 CSV 列名不同，先依据字段表转换；不是把任意表格直接上传。不能解析的表格先由提供方修正，未提供的数据留空状态。

## 7. 状态与日常处理

| 状态 | 用户应看到 | 处理动作 |
| --- | --- | --- |
| 已获取 | 有效真实值、来源、业务截止和期间 | 正常使用；定期对账 |
| 部分覆盖 | 有限范围真实值和覆盖限制 | 列出未接入渠道/对象，不能称部门总量 |
| 未采集 / 未接入 | 灰色 `—` 及缺口 | 指定来源责任角色，安排首批导出 |
| 未配置 / 未评估 | 灰色 `—` 及缺定义/评估说明 | 先确认口径或评估，不填估计等级 |
| 不适用 | 比例分母为零说明 | 核实分子分母确为零；不能按失败或 0% 解读 |
| 过期 | 保留最后真实值并灰显，显示业务截止 | 联系来源取得新批次；刷新页面不会更新业务截止 |
| 读取失败 / 无权限 | 错误提示，有旧值则灰显 | 核实后台会话、部门权限和网络；不要改填 0 |
| 预检/版本冲突 | 未写入提示 | 重新读取当前数据，再预检；不能强行覆盖 |

默认有效期为 24 小时，可由每条真实记录的 `validForHours` 在允许范围内配置。源系统每周/月更新时应按已确认的业务时效设置，不要通过反复导入旧数据掩盖过期。

`asOf` 是业务源截止，`receivedAt` 是成功导入的接收时间；读取响应的 `fetchedAt` 只表示本次网站响应生成时间，`updatedAt` 只表示最近导入接收时间（没有导入时为 `null`）。这些时间不能相互替代，也不能据此宣称页面刷新已重新抓取外部来源。

## 8. 首批验收与发布前核对

- [ ] 部门名称、稳定 ID、管理员角色、人员 username 映射已确认；其他部门不能读取或写入。
- [ ] 指标、单位、期间、来源权威性、业务 `asOf`、历史覆盖和全年目标定义已确认。
- [ ] 每类实际导入的量/率与源系统同范围结果核对；比例分母、真实 0、部分覆盖和无数据能区分。
- [ ] 来源时间与接收时间分开；刷新后持久化可读；旧批次不重复累计；旧截止时间不会覆盖新值。
- [ ] 缺数、过期、读取失败保持灰色且可解释；历史未采集不补曲线；集团人才示例未混入部门实数。
- [ ] 来源责任角色、刷新/导出频率、失败联系人及历史补数安排已明确。
- [ ] 已完成本地功能验证；需要正式发布时另行获得授权，发布后再做生产页面和真实来源核验。

待建设项：外部来源实际 URL 与能力、服务身份授权、自动同步调度与受限重试、来源优先级治理、正式口径与责任人。上述项由供数/运维角色逐项确认，不阻碍继续人工导入已经核验的数据。
